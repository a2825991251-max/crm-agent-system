# 青杉 CRM · 4 Agent 主动跟进系统

这是一个可直接运行的 CRM 原型，核心链路是：

`300 条历史对话 → Agent 1 识别问题与证据 → Agent 2 制定触达策略 → Agent 3 生成并定时发送询问 → Agent 4 审核后放行`

## 四个 Agent

- Agent 1：压缩长对话，区分事实与主观情绪，生成客户画像、证据索引和 `issue_registry`。
- Agent 2：不再生成课程方案。它根据问题严重度决定是否联系、联系家长还是学生、在第几天联系、何时暂停以及何时转人工。
- Agent 3：严格执行 Agent 2 的策略，为每个问题生成一条主动询问，并写入 CRM 定时发送队列。它不承诺提供记录、报告或阶段总结。
- Agent 4：校验事实与问题引用、触达频率、停止条件、策略执行、违规宣传、额外运营承诺、CRM 字段和隐私。

演示客户会生成三次主动询问：第 7 天跟踪函数问题、第 15 天询问错题复盘、第 30 天确认反馈透明度顾虑。30 天最多联系 3 次，最小间隔 7 天；连续两次未回复或家长要求停止时暂停。

工作台支持在 8 位演示学生之间切换。每位学生的 Agent 运行结果、SOP 和发送任务相互隔离；首次打开或切换到尚未分析的学生时，SOP 与任务区保持为空，只有当前学生成功运行完整的四 Agent 链路后才会生成。Agent 4 未放行的学生仍不会获得可发送 SOP。

“导入对话”窗口提供一键载入 300 条模拟长对话。样本会自动匹配当前选中的学生，跨约两个月，混合关键事实、重复确认、日常闲聊、改期、待确认信息和家长主观情绪，适合测试 Agent 1 的压缩、降噪及事实区分能力。样本完全虚构，不包含真实个人信息。

无需执行导入也可以直接测试：8 位演示学生的“对话记录”已经预置真实业务风格的完整虚构聊天。林梓轩有 300 条，其余学生按各自客户档案中的消息数量展示；切换学生时同步切换对应聊天，数据互不混用。

点击“导入并运行 Agent”后，对话会先同步到当前学生的“对话记录”页，再进入四 Agent 分析。新导入内容会使该学生此前的 Agent 结果和 SOP 失效；即使本次 Agent 请求失败，已经导入的对话仍保留在当前浏览器会话中，便于检查和重试。

## 运行

无需安装第三方依赖：

```bash
python3 server.py
```

访问 `http://127.0.0.1:4173`。客户、Agent 产物和排期保存在本机 `data/crm.sqlite3`。

## 启用 AI

AI 密钥只由本地服务读取，不会进入网页、聊天产物或 SQLite。系统已经预设 Cub2API：

发布到 GitHub 前请确认：`.env.local`、任何 `.env.*.local`、编辑器 swap 文件和 `data/*.sqlite3` 都已被 Git 忽略。仓库只提交 `.env.example`，其中不包含真实 Key。页面和状态接口只返回“已配置”状态，不返回 Key 或末尾片段。若 Key 曾被误提交、粘贴到公开 issue，或出现在构建日志中，应立即在对应服务控制台撤销并重新生成。

```bash
cp .env.example .env.local
```

然后只在本机编辑 `.env.local`，填写 `AI_API_KEY`，并把 `AI_MODEL` 改为 Cub2API 控制台中该密钥实际可用的 GPT 模型名。默认服务地址是 `https://cubapi.codemao.cn/v1`，走 OpenAI Responses 兼容接口。

`.env.local` 已加入忽略清单，不应发送到聊天、网页或提交到代码仓库。环境变量 `AI_API_KEY`、`AI_MODEL`、`AI_API_BASE`、`AI_API_PROTOCOL` 也可以直接覆盖文件配置；旧的 `OPENAI_API_KEY`、`OPENAI_MODEL`、`OPENAI_API_BASE` 仍兼容。接口格式支持自动兼容 Responses API 和 Chat Completions API。

未配置密钥时系统使用规则模式；AI 网络失败、拒绝请求或返回无效结构时，整条运行自动回退到规则模式，并在客户工作台显示实际运行模式和中转服务名称。

AI 执行方式：

1. Agent 1 先在本地处理完整对话，按证据锚点、信息密度、角色和时间分布去重筛选，默认最多向 AI 提交 64 条或约 12,000 字符，并设置 60 秒独立超时。300 条对话通常只需要 1 次提炼请求；原始消息仍全部保留在 CRM，证据引用继续指向原始编号。若中转站超过 60 秒仍未响应，系统会切换到规则模式完成后续链路。
2. Agent 2 使用确定性规则对 Agent 1 已识别的问题排序并生成询问目标，不再增加一次模型往返；联系时间和停止条件同样由代码固定。
3. Agent 3 生成自然的主动询问内容，发送时间、CRM 字段和策略引用由代码补齐。
4. Agent 4 先做确定性规则审查，再做 AI 语义审查；任一闸门不通过都不能发布。

运行时右侧 Agent 链路显示后端真实进度。Agent 1 会显示当前正在压缩的对话分块，随后依次流转到 Agent 2、Agent 3 和 Agent 4；已完成节点和连线变为绿色，当前节点高亮为蓝色，顶部同时显示阶段百分比与耗时。页面通过运行任务状态接口轮询进度，不使用前端假动画。

启用 AI 后，导入的历史对话会发送到配置的第三方中转服务用于本次分析，请在生产环境接入前完成客户授权、隐私告知，并确认中转站的日志、数据保留和二次使用政策。请求设置 `store: false`，但中转站是否完整透传并遵守该字段取决于其实现，不能替代组织自身的隐私与合规流程。

## 定时发送

顾问确认 Agent 3 生成的时间和消息后，可以一键写入发送队列。配置发送网关：

```bash
CRM_SEND_WEBHOOK_URL="https://你的发送网关地址" python3 server.py
```

到期时系统向网关发送：

```json
{
  "schedule_id": "...",
  "channel": "wecom",
  "recipient_external_id": "wm_xxxxxx",
  "content": "需要发送给家长的合规询问"
}
```

网关返回 HTTP 2xx 后才标记为已发送。失败最多重试三次；未配置网关时任务保持“等待发送通道”，不会误标为已送达。网关后可接企业微信客户联系 API、短信或微信服务号客服消息 API。

已启用的 SOP 可以进入“修改排期”模式，手动调整未来任务的发送日期、时间、正文、渠道和收件人，也可以取消勾选某条未来任务。保存修改时会重新检查消息是否为纯询问、是否包含违规宣传或额外交付承诺，以及任务间隔和 30 天触达上限。已经实际发送的消息保持只读。

## 执行保护

- Agent 4 `PASS` 的版本可以直接进入发送队列；未通过的版本必须记录人工审核人、时间和确认意见后才能放行。
- 没有 Agent 1 问题证据时，不生成问题型触达。
- Agent 2 每条策略必须引用一个 Agent 1 问题，并包含“家长要求停止联系”。
- Agent 3 每条消息必须引用一个 Agent 2 策略和一个 Agent 1 问题。
- 队列层再次检查：最多 3 条、间隔至少 7 天、周期不超过 30 天。
- 顾问修改正文后再次检查绝对化宣传和额外交付承诺。
- 上游产物变更后，下游必须重新生成并由 Agent 4 全量复审。

## 主要接口

```text
POST /api/ai/config
POST /api/runs
GET  /api/runs/:runId
GET  /api/channels
GET  /api/ai/status
GET  /api/schedules?customer_id=:customerId&run_id=:runId
POST /api/schedules/bulk
PUT  /api/schedules/bulk
```

前端“发送演示”是沙盒，只演示等待、发送中、失败重试和送达状态，不会联系真实客户。
